# Replica Monitor

Проверка основной таблицы и реплики по количеству строк, максимальной дате и свежести обновления. Поддерживаются MySQL/MariaDB и ClickHouse. Результаты выводятся в консоль и, при необходимости, в новый Excel-отчёт.

Каждый запуск выполняет один проход по выбранному YAML-пресету. Встроенного расписания нет.

## Быстрый старт

Команды ниже выполняются из корня проекта в PowerShell:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

Код использует синтаксис Python 3.10+. Доступность конкретных закреплённых версий зависимостей для выбранной версии Python и ОС проверяется при установке. Для MySQL используется драйвер `mysqlclient`.

1. Создайте `.env` в корне проекта по примеру ниже.
2. Создайте или заполните YAML-пресет в `Presets`.
3. Запустите:

```powershell
.\.venv\Scripts\python.exe main.py
```

Корневой `main.py` загружает окружение, выполняет проверки, сохраняет Excel и пытается открыть папку отчёта. Для запуска из другой рабочей папки укажите полные пути к интерпретатору и `main.py`.

## Переменные окружения

Пример `.env` с условными реквизитами:

```dotenv
ROOT_DIR=D:/Programming/python/Projects/replica-monitor
CONFIG_PATH=D:/Programming/python/Projects/replica-monitor/Presets
CONFIG_NAME=config.yaml
OUTPUT_=D:/Programming/python/Projects/replica-monitor/Reports

MYSQL_HOST=localhost
MYSQL_PORT=3306
MYSQL_USER=monitor
MYSQL_PASSWORD=replace_me

CLICKHOUSE_HOST=localhost
CLICKHOUSE_PORT=8123
CLICKHOUSE_USER=monitor
CLICKHOUSE_PASSWORD=replace_me
```

| Переменная | Назначение |
| --- | --- |
| `ROOT_DIR` | Рабочая папка: `load_env()` переходит в неё |
| `CONFIG_PATH` | Папка YAML-пресетов |
| `CONFIG_NAME` | Имя файла с расширением `.yaml` или `.yml`, без пути |
| `OUTPUT_` | Папка отчётов; обязательна только при экспорте |
| `MYSQL_*` | Параметры подключения MySQL/MariaDB |
| `CLICKHOUSE_*` | Параметры подключения ClickHouse через HTTP-интерфейс |

`.env` загружается относительно расположения проекта. Уже заданные переменные окружения имеют приоритет. Параметры БД нужны при создании соответствующего подключения; текущие обёртки требуют непустой пароль. Для запросов необходим доступ к таблицам, а для проверки колонки даты — к метаданным источника.

Базы и таблицы задаются в YAML. Переключение пресета выполняется заменой `CONFIG_NAME`. Не включайте реальные пароли в публикуемые файлы.

## YAML-конфигурация

```yaml
tables:
  - name: orders
    primary:
      type: mysql
      database: app
      table: orders
      datetime_column: updated_at
      last_update_column: null
      final: false

    replica:
      type: clickhouse
      database: replica
      table: orders
      datetime_column: updated_at
      last_update_column: loaded_at
      final: true

    strategy:
      row_count: true
      lag_check: true
      last_update: true

    rules:
      max_row_diff: 20
      max_lag_seconds: 3600
      last_update_seconds: 86400
```

Имена таблиц и колонок в примере необходимо заменить на существующие в ваших БД.

### Источники

`name` — уникальное имя проверки внутри пресета. `primary` и `replica` имеют одинаковую структуру:

| Поле | Описание |
| --- | --- |
| `type` | `mysql` или `clickhouse`; обе стороны могут иметь один тип |
| `database` | База/схема источника |
| `table` | Имя таблицы |
| `datetime_column` | Колонка максимальной даты для проверки отставания |
| `last_update_column` | Колонка даты записи/обновления для проверки свежести |
| `final` | Добавляет `FINAL` для ClickHouse; по умолчанию `true`, для MySQL `false` |

Неиспользуемые колонки дат можно опустить или указать `null`. Для включённого `lag_check` колонка `datetime_column` нужна с обеих сторон. SQL-идентификаторы допускают латинские буквы, цифры и подчёркивания, но не могут начинаться с цифры.

### Типы полей и допустимые значения

Типы соответствуют моделям в `Code/config.py`:

| Поле | Тип / значения в YAML | Можно `null`? | Если поле пропущено |
| --- | --- | --- | --- |
| `tables` | Список настроек таблиц | Нет | Ошибка |
| `name` | Строка, уникальная в пресете | Нет | Ошибка |
| `primary`, `replica` | Объект описания источника | Нет | Ошибка |
| `primary.type`, `replica.type` | `mysql` или `clickhouse` | Нет | Ошибка |
| `database`, `table` | Строка с именем базы или таблицы | Нет | Ошибка |
| `datetime_column`, `last_update_column` | Строка с именем колонки или `null` | Да | `null` |
| `final` | Флаг: `true` / `false` или `1` / `0` | Нет | `true`; для MySQL нормализуется в `false` |
| `strategy` | Объект флагов | Нет | Включён только `row_count` |
| `strategy.row_count` | Флаг: `true` / `false` или `1` / `0` | Нет | `true` |
| `strategy.lag_check`, `strategy.last_update` | Флаг: `true` / `false` или `1` / `0` | Нет | `false` |
| `rules` | Объект допусков | Нет | Ошибка; допустим пустой объект `{}` |
| `rules.max_row_diff` | Целое число ≥ 0, количество строк | Нет | `0` |
| `rules.max_lag_seconds`, `rules.last_update_seconds` | Целое число ≥ 0, секунды | Нет | `0` |

**`null` разрешён только у двух полей колонок дат внутри источников.** Весь блок источника, его тип, база и таблица не могут быть `null`.

Стратегии — бинарные переключатели. Правила — числовые допуски: например `0`, `20`, `3600`, `86400`. Ноль в правиле разрешён и означает нулевой допуск, а не отключение проверки.

```yaml
strategy:
  row_count: 1
  lag_check: 0
  last_update: 0
rules:
  max_row_diff: 0
  max_lag_seconds: 3600
  last_update_seconds: 86400
```

Это проверка количества строк без допустимого расхождения; временные проверки отключены независимо от значений их правил.

Для отсутствующей колонки используйте `null` без кавычек. `"null"` — обычная строка, которая будет воспринята как имя колонки. Пустое значение после двоеточия YAML также читает как `null`.

Модели Pydantic используют обычную, не строгую валидацию и могут преобразовывать некоторые совместимые значения, например строковые числа. Для однозначной конфигурации записывайте флаги и числа без кавычек, как в примерах выше.

### Стратегии и допуски

| Стратегия | Правило | Условие успешной проверки |
| --- | --- | --- |
| `row_count` | `max_row_diff` | `abs(primary_count - replica_count) <= max_row_diff` |
| `lag_check` | `max_lag_seconds` | `primary_max_date - replica_max_date <= max_lag_seconds` |
| `last_update` | `last_update_seconds` | `collected_at - update_date <= last_update_seconds` |

Временные допуски задаются в секундах: 12 часов — `43200`, сутки — `86400`. Граница допуска включается в успешный результат.

- Проверку включает только флаг `strategy`. Значение правила не является переключателем.
- Нулевой допуск разрешён, отрицательный запрещён.
- Если `strategy` не указан, включена только проверка количества строк.
- Блок `rules` обязателен; пропущенные внутри него допуски равны нулю.
- В `strategy`, `rules` и `final` нельзя оставлять `null` в рабочем пресете. Такие значения пригодны только для незаполненного шаблона.
- Неизвестные поля и повторяющиеся `name` отклоняются при загрузке конфигурации.

Для `last_update` основная таблица и реплика проверяются независимо, если дата доступна. Отсутствующая дата пропускается. Если нет обеих дат, результат — `WARNING`, если другая проверка уже не дала `ERROR`.

## Даты и системное время

Время сбора фиксируется отдельно для каждого источника непосредственно перед запросом через `datetime.now()`. Свежесть рассчитывается относительно этого времени, а не относительно конца проверки всех таблиц. `checked_at` — время формирования результата.

- Дата из БД без пояса используется как местное время без сдвига.
- Дата с поясом переводится в системный часовой пояс, затем сравнивается с локальным временем.
- Отдельной настройки `timezone` в конфиге нет.
- В отчёте показываются исходные значения драйвера из полей `*_raw`.
- Строки `ДД.ММ.ГГГГ` преобразуются перед разбором; неверные даты дают ошибку проверки. Числовые Unix timestamp автоматически не распознаются.
- Будущие даты допустимы: возраст отрицательный и проходит верхний порог свежести.
- Реплика с максимальной датой впереди основной не считается отстающей.

В текущем SQL для ClickHouse даты предварительно форматируются через `formatDateTime` в строки без пояса. Поэтому пояс и формат результата SQL должны соответствовать локальному времени машины мониторинга. Для свежести используйте колонку фактической записи, если хотите контролировать именно время загрузки данных.

## Использование из Python или ноутбука

Воспользуйтесь `Start/Start_from_jupiter.ipynb` или используйте вариант представленный ниже

Корень проекта должен быть доступен для импорта `Code`.

```python
from Code.load_env import load_env
from Code.monitor import run_checks

load_env()
run = run_checks(create_xlsx=True, open_folder=False)

for result in run.results:
    print(result.table_name, result.status, result.comment)

print(run.report_path)
```

`run_checks()` сам не вызывает `load_env()`: окружение подготавливает вызывающий код.

| Аргумент | По умолчанию | Назначение |
| --- | --- | --- |
| `create_xlsx` | `False` | Сохранять Excel |
| `open_folder` | `True` | Открыть папку после экспорта |
| `mysql_conn` | `None` | Готовый объект `MySQLConn` |
| `clickhouse_conn` | `None` | Готовый объект `ClickHouseConn` |

Возвращается `RunResult`:

- `results`: список `CheckResult`, включая ошибки сбора;
- `rows`: готовые словари строк отчёта;
- `report_path`: путь `Path` к Excel или `None` без экспорта.

`CheckResult` содержит статус, комментарий, разницу строк, отставание, возраст обновлений, время сбора каждой стороны, разобранные и исходные даты. При недоступности метрики соответствующие значения могут быть `None`.

### Переиспользование подключений

```python
from Code.db import MySQLConn, ClickHouseConn

# Окружение уже загружено.
mysql = MySQLConn()
try:
    clickhouse = ClickHouseConn()
    try:
        run = run_checks(mysql_conn=mysql, clickhouse_conn=clickhouse)
    finally:
        clickhouse.close()
finally:
    mysql.close()
```

Коллектор переиспользует одно подключение на тип источника. Созданные им подключения закрываются после сбора; переданные извне закрывает вызывающий код. Конфигурация подключения рассчитана на один сервер каждого типа за запуск.

## Статусы и Excel

| Статус | Значение | Цвет строки |
| --- | --- | --- |
| `OK` | Выполненные проверки прошли | Зелёный |
| `WARNING` | Все проверки отключены или нет обеих дат обновления при включённой проверке свежести | Жёлтый |
| `ERROR` | Превышен допуск, неверная дата или ошибка получения/проверки метрик | Красный |

Предупреждение не перекрывает ошибку другой проверки. Ошибка сбора одной пары таблиц не останавливает обход остальных. В комментарий включаются путь YAML и причина ошибки источника. Ошибки загрузки конфигурации и сохранения отчёта могут завершить весь запуск.

Каждый экспорт создаёт новый `.xlsx` с уникальным именем в `OUTPUT_`. Папка создаётся автоматически. Отчёт содержит время проверки, основную таблицу, реплику, статус, комментарий, фактические метрики и применённые допуски. Расчёты для отчёта повторно не выполняются.

Экспортёр можно использовать отдельно:

```python
from Code.report import export_report

path = export_report(run.rows, "Reports", open_folder=False)
```

Открытие папки поддерживается средствами Windows, macOS и Linux. Ошибка открытия папки не отменяет сохранение файла.

## Ограничения

Совпадение количества строк и максимальных дат не доказывает равенство содержимого таблиц. Источники читаются последовательно, поэтому изменения между запросами могут давать временную разницу. `COUNT`, `MAX` и особенно `FINAL` могут быть затратными на больших таблицах; включайте только необходимые проверки.

Программа выполняет один проход. Для регулярных запусков используйте внешний планировщик. Статусы таблиц находятся в `RunResult` и отчёте: корневой скрипт не устанавливает отдельный ненулевой код завершения при статусе `ERROR` таблицы.
